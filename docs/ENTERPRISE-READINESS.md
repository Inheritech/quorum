# Enterprise readiness and retention research

Research date: 2026-09-24. This is an engineering assessment of the application and official published vendor information. Applicable obligations and contracts must be reviewed for the customer’s jurisdiction and data classification. Neither vendor attestations nor this implementation certify the application.

## Decision

The requested Vercel + Convex stack can support **end-to-end encrypted, short-lived sessions**. It cannot truthfully promise that no data is ever persisted: Convex is a persistent database, and vendors retain operational information. A deleted document is not evidence that every replica, transaction record, backup, diagnostic artifact, or downstream copy has been erased.

The product distinguishes confidentiality from retention: room content is encrypted before upload, and retained provider copies remain ciphertext unreadable without the invitation-derived key. The application does not give the operator or providers that key. Metadata, including connection and activity information, is separate. The UI leads with that protection, explains deletion on demand, and does not claim certification or use compliance as product copy.

If a customer requires literally zero persistent session data anywhere, this architecture does not meet that definition. Options to investigate are an audited ephemeral relay or peer-to-peer transport with browser-held state, memory-only signaling, and negotiated metadata retention. Convex could not remain the persistence layer for those sessions. Such an alternative has reconnection, durability, host availability, networking, and abuse-control tradeoffs; it has not been implemented here.

## Controls implemented

| Control                 | Current behavior                                                                                                                                                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content confidentiality | Browser-side AES-GCM; room keys unavailable to either backend. See the construction and threat boundaries in `SECURITY.md`.                                                                                                                       |
| Minimal identity        | Optional pseudonymous display name only; no email or account. Session tokens are random capabilities, stored hashed.                                                                                                                              |
| Admission               | Host approval on by default, pending guest isolation, optional room lock, host-only privileged actions.                                                                                                                                           |
| Secret-safe URLs        | Invitation secret in the fragment; no room name, item name, or room identifier in a route or query. Referrers disabled.                                                                                                                           |
| No integrations         | Item links are ordinary optional hyperlinks. No link scraping, trackers, analytics, or remote fonts.                                                                                                                                              |
| Application retention   | Absolute deadline, scheduled deletion, sweep backstop, host deletion, participant removal, no completed-item or vote history.                                                                                                                     |
| Client retention        | Room plaintext stays in memory. Invitation and session capability use tab-scoped sessionStorage for refresh recovery, cleared on leave/observed removal/expiry. Browser restoration may preserve credentials; room name appears in the tab title. |
| Hardening               | Script nonce CSP, security headers, bounded payloads and membership, capability checks, round/version checks, encrypted field padding.                                                                                                            |
| Verification            | Cryptographic boundary tests, backend authorization/retention integration tests, and desktop/mobile browser tests. No external penetration test performed.                                                                                        |

## Required decisions and work before enterprise rollout

1. **Define data classes and the retention promise.** Inventory plaintext, ciphertext, capabilities, access metadata, provider logs, backup copies, browser storage outside app control, and external invitation channels. Agree what “zero retention” actually means. Document expiry targets and what happens during outages, suspension, and restores.
2. **Obtain written vendor commitments.** Ask Vercel and Convex about log/diagnostic payload capture, transaction history, replica deletion, backup retention/expiry, support access, storage regions, incident notification, and deletion evidence. Confirm settings for the specific plans; a provider-wide certification alone is insufficient.
3. **Complete privacy governance.** Document controller/processor roles, lawful basis, notice, subprocessors, data transfers, rights-request procedure, and security/retention records. Determine whether a DPIA or another risk assessment is required. Content encryption and anonymous access do not make IP addresses or identifiable ticket names non-personal.
4. **Choose access policy.** Some organizations will require SSO/SAML, managed devices, network restrictions, named host accountability, or tenant isolation. These requirements cannot all be satisfied by unverifiable anonymous invitations. Keep anonymous mode for appropriate data classes; design a separate enterprise access tier if required. Tenant policy enforcement and SSO are not currently implemented.
5. **Commission cryptographic and application review.** Review the shared-secret model, nonce usage, capability authorization, group membership, no-forward-secrecy limitation, and release timing. Audit the deployed frontend and supply chain. Decide whether per-member keys, signed builds, cryptographic commit/reveal, or forward secrecy are required.
6. **Harden operations.** Apply organization MFA/SSO and least privilege to Vercel, Convex, source hosting, and CI. Protect production changes, rotate deployment credentials, isolate previews, disable unused exports, configure budget/usage caps, and add abuse controls that protect direct Convex endpoints. Establish patching, dependency scanning, incident response, and deletion-failure monitoring without logging content.
7. **Resolve accountability versus no history.** Enterprise customers may need administrative audit events and incident evidence. Define a separate, minimal operational audit stream, access policy, retention, and customer consent. Never place names, invitations, URLs, votes, ciphertext bodies, or session tokens into audit messages by default. No audit stream is implemented here.
8. **Validate special regimes.** If PHI is in scope, confirm applicable BAAs and supported products with **both** vendors; do not enable it just because one advertises HIPAA support. Evaluate financial, public-sector, contractual residency, accessibility, and other customer-specific controls separately. Restrict sensitive data until that review is complete.

## Production acceptance checklist

- [ ] Customer data classes and an accurate retention statement are approved.
- [ ] Applicable DPAs, transfer mechanisms, subprocessors, and vendor retention commitments are documented.
- [ ] Region choice, backup/restore policy, log capture, and integration settings are reviewed for both platforms.
- [ ] A configured real deployment passes host/voter/observer and admission tests in independent browsers.
- [ ] Network inspection confirms no invitation secret, key, name, item detail, or vote plaintext leaves the client.
- [ ] Scheduled deletion and the cron backstop are tested on a real deployment, including outage/restore procedures.
- [ ] Production frontend integrity, CSP, dependency risks, and E2EE construction receive independent security review.
- [ ] Backend-facing abuse protection, quotas, monitoring, incident response, and private security contact are operational.
- [ ] Customer-specific identity, tenancy, audit, accessibility, and regulatory requirements are met or explicitly out of scope.

These items are rollout gates, not claims of controls already present. This repository is ready for configuration and further evaluation; it is not independently certified for enterprise use.
